# Stolen Realm — Skill Weight Mod

Biases roguelike skill offerings toward (or away from) the skills a character already has,
instead of vanilla's uniform draw within a tier.

## What it actually changes

Vanilla `RoguelikeManager.GetSkillChoices` builds a pool of eligible skills, rolls a tier per
option, then picks uniformly at random from that tier:

```csharp
chosenSkills.Add((from x in list
    where !chosenSkills.Contains(x) && x.Tier == tierToRoll
    orderby UnityEngine.Random.value
    select x).First());
```

This mod replaces the method with a Harmony prefix that reproduces the eligibility pool, the
tier roll and the per-tier maximums **exactly**, and changes only that last line into a
weighted pick.

Deliberately unchanged: which tier you roll, how many options you get, per-tier caps,
DLC/disabled/replaced filtering, and the exclusion of skills you already own.

## Installing / enabling

The mod is loaded by [BepInEx 5](https://github.com/BepInEx/BepInEx) via its doorstop hook, so
there is no launcher and no launch option — once the files are in place, **starting the game
from Steam normally is all that is required**.

Layout inside the Stolen Realm install directory:

```
Stolen Realm/
  winhttp.dll                                  <- doorstop hook (BepInEx)
  doorstop_config.ini                          <- must contain: enabled = true
  BepInEx/
    core/                                      <- BepInEx itself
    plugins/SkillWeightMod/SkillWeightMod.dll  <- this mod
    config/bfivealive.stolenrealm.skillweightmod.cfg  <- generated on first run
    LogOutput.log                              <- generated on first run
```

From a clean install that means: unzip the BepInEx 5 **x64** release into the game folder, then
drop `SkillWeightMod.dll` into `BepInEx/plugins/`. `dotnet build` does the second step for you.

### Confirming it loaded

Launch the game, then look in `BepInEx/LogOutput.log` for:

```
[Info   :Skill Weight Mod] Skill Weight Mod 0.1.0 loaded. SynergyStrength=1
```

Note that BepInEx ships with its console **disabled** (`Enabled = false` under
`[Logging.Console]` in `BepInEx/config/BepInEx.cfg`). `LogRolls` output therefore lands in
`LogOutput.log` rather than in a visible window. Set that to `true` if you would rather watch
rolls live while tuning.

### Disabling

- `SynergyStrength = 0` in the mod config — vanilla rolls, the patch short-circuits.
- Delete `BepInEx/plugins/SkillWeightMod/` — mod gone, BepInEx stays.
- `enabled = false` in `doorstop_config.ini` — all modding off, game fully vanilla.

## Weighting

Each candidate starts at weight `1.0`. Four signals adjust it, all read off the character's
own `SkillsFromPoints`:

| Signal | Effect |
|---|---|
| `TreeAffinity` | Per owned skill in the same tree (Fire, Warrior, Shadow, …). |
| `BroadAffinity` | Per owned skill sharing a **broad** category, times that category's weight. |
| `NarrowAffinity` | Per owned skill sharing a **narrow** category, times that category's weight. |
| `DependencyBonus` | Flat, when you already own the candidate's prerequisite. |

Those sum into a synergy score, which is scaled by `SynergyStrength`, damped for repetition,
then clamped:

```
synergy = TreeAffinity   * (owned in same tree)
        + BroadAffinity  * SUM over shared broad  categories of BroadWeight[c]  * (owned sharing c)
        + NarrowAffinity * SUM over shared narrow categories of NarrowWeight[c] * (owned sharing c)
        + DependencyBonus if the prerequisite is owned

weight  = 1 + SynergyStrength * synergy
weight  = weight * OfferedDecay ^ min(timesOffered, MaxOfferedPenaltyStacks)
weight  = clamp(weight, MinWeight, MaxWeight)
```

- `SynergyStrength = 0` → vanilla behaviour (the patch short-circuits entirely).
- `SynergyStrength = 1` → default specialisation.
- `SynergyStrength < 0` → **inverts** the system and pushes rolls toward skills unlike what
  you already have, if you'd rather the game forced variety.

`MinWeight` keeps every skill reachable; `MaxWeight` stops a deep specialisation from
completely crowding out the rest of the tier.

### Categories

The two category tiers come from [`skill-tags.md`](skill-tags.md) — 15 broad and 39 narrow,
documented there in full. Every skill's membership is generated by `tools/taxonomy.py` into
`skill-categories.json`, which **the mod loads at startup**. The classification rules exist in
exactly one place; there is no second implementation in C# to drift out of sync.

Each category gets its own config entry under `[Broad Weights]` or `[Narrow Weights]`, so a
narrow path like Poison can pull harder than a broad one like Damage without touching the four
master levers. Setting a category to `0` ignores it entirely.

**Shipped defaults are inverse-frequency**: `379 / the number of skills carrying the category`.
A category on 5 skills is a far sharper signal than one on 225, so this makes the default mean
"equal pull per unit of rarity" rather than "equal pull". Expect large numbers for rare
categories — `Bleed` starts at 75.8 — and set `MaxWeight` high enough that the clamp is not
swallowing the spread.

Adding a category to `tools/taxonomy.py` and regenerating is enough to make it tunable; the mod
binds a config entry for whatever it finds in the JSON.

### Repetition damping

Declining a skill does **not** remove it from the eligible pool. Without any correction, a
heavily weighted skill is re-offered at full weight at every single level-up, which is what
makes a specialised run feel like it keeps showing the same three things.

So each character keeps a per-run count of how many times a skill has been *offered* to them,
taken or not, and `OfferedDecay` (default 0.5) multiplies weight by that factor per prior
offer:

| Times offered | Weight multiplier at 0.5 |
|---|---|
| 0 | 1 |
| 1 | 0.5 |
| 2 | 0.25 |
| 3 | 0.125 |
| 4+ | 0.0625 (capped by `MaxOfferedPenaltyStacks`) |

Set `OfferedDecay = 1.0` to switch the mechanic off, or lower it (0.25) to punish repeats
harder. `MaxOfferedPenaltyStacks` (default 4) bounds the compounding so a much-offered skill
becomes rare rather than impossible.

The decay is applied *before* the clamp, so `MinWeight` remains a genuine floor.

This works with `SynergyStrength = 0` too, if all you want is vanilla-flavoured rolls that stop
repeating themselves.

**Lifetime.** History is keyed on the `Character` instance through a `ConditionalWeakTable`, so
it covers one run and disappears with the character — a new run builds new `Character` objects
from presets and starts clean. It is in-memory only: quitting to the menu and reloading a run
in progress resets the counts. Rerolls are counted as offers, which is intended.

## Reroll button

Adds a **Reroll** button to the skill-selection window that redraws the offered skills for a
health and mana price.

- **Cost:** 50% of maximum health and 50% of maximum mana (`RerollHealthCost`, `RerollManaCost`).
- **Greyed out** at or below 50% of max health, or at or below 50% of max mana
  (`RerollHealthThreshold`, `RerollManaThreshold`).
- Characters with no mana pool ignore the mana half entirely, for both cost and threshold.
- Set `RerollEnabled = false` to remove the button.

### Cost basis

`RerollCostFromMaxPool` (default `true`) decides what "50%" is measured against:

- `true` - the cost is 50% of your **maximum** pools. A flat price, and what makes the
  threshold load-bearing: requiring more than 50% before allowing the purchase is exactly what
  guarantees the payment cannot take you to zero.
- `false` - the cost is 50% of your **current** pools, i.e. it halves whatever you have left
  and asymptotically approaches zero without reaching it.

The first reading is the default because it makes the greying-out rule do real work rather than
being decorative. Flip it if the other feel is wanted.

### How it is built

The button is a **clone of the window's existing Accept button**, reparented as its sibling, so
it picks up the game's own styling instead of reproducing it. Two details that matter:

- `onClick.RemoveAllListeners()` does *not* clear listeners wired up in the Unity inspector, and
  the clone inherits Accept's. The whole `ButtonClickedEvent` is replaced instead.
- The clone gets a `LayoutElement` with `ignoreLayout = true` and is pinned to the **top-right
  corner of the panel** by setting its anchor, pivot and anchored position all to that corner.
  No measuring is involved, so the placement holds at any resolution or UI scale.

  It stays parented to Accept's own parent (`Content`), which is the panel's content root.
  `RoguelikeManager.SkillSelectWindow` looks like the obvious anchor but is **not** the panel -
  that object spans the whole screen, so anchoring to it put the button in the screen's top-right
  corner, well outside the visible window.

  An earlier version instead tested `parent.GetComponent<LayoutGroup>()` and only offset the
  button when that returned null. That failed: a **disabled** `LayoutGroup` still returns
  non-null while performing no layout, so the offset was skipped and the button rendered exactly
  on top of Accept. Opting out of layout and positioning explicitly avoids depending on the
  parent's configuration at all.
- Placement knobs, all live-reloadable: `RerollButtonMarginX` / `RerollButtonMarginY` (default
  32) set the distance from the window's right and top edges, `RerollButtonScale` (default 0.75)
  sizes the button relative to Accept, and `RerollButtonOffsetX` / `RerollButtonOffsetY`
  (default 0) are extra nudges - positive X moves right, positive Y moves up.
- The label reads **Reroll** with a smaller cost line beneath it, sized by `RerollSubtextScale`
  (default 55, a percentage of the main font). The cost line shows percentages rather than
  absolute values, and those percentages are read from `RerollHealthCost` / `RerollManaCost`
  rather than hardcoded, so it stays truthful if the costs are retuned. Characters with no mana
  pool get an HP-only line.

Rerolling re-invokes the game's private `PopulateSkillChoices` through reflection with the exact
arguments of the original roll, captured by a postfix. That preserves `ForcedTier`, which is not
recoverable from anywhere else once the window is open.

Health and mana are written via `character["Health"]`, which is how the game does it itself (see
`Character.SetHealthAndManaToMax`), so the observable sync layer picks the change up normally.

Rerolled offers are recorded in the repetition history like any others, so rerolling damps the
skills you just rejected.

## Config

Tuning lives in `BepInEx/config/bfivealive.stolenrealm.skillweightmod.cfg`, generated on first
run. Edit between runs; no rebuild needed.

Set `LogRolls = true` to print each roll's top candidates with their weights and resulting
percentages to the BepInEx console — the fastest way to sanity-check a retune.

### Live config reload

BepInEx reads a plugin's config once at startup and never watches the file - `BepInEx.dll`
contains no `FileSystemWatcher` at all - so by default every tweak costs a game restart.

`HotReloadConfig` (default `true`) adds one. Save the `.cfg` and the change applies without
restarting: every value is read fresh at the point of use, so a new weight takes effect on the
next roll and a button offset on the next frame.

Cost is nil. `FileSystemWatcher` is driven by OS change notifications rather than polling, so it
is completely idle until the file is written; the only per-frame work is two boolean checks.

Two details the implementation has to handle:

- Watcher callbacks arrive on a thread pool thread. They only set a `volatile bool`; the reload
  itself happens on the main thread in `Update`.
- Editors emit several events per save, and `Config.Reload()` makes BepInEx write the file back
  out, which the watcher then sees as another change. A 0.3s debounce collapses the first burst
  and a 0.75s ignore window after each reload breaks the self-write echo. Without the second
  guard, one save produced two reloads.

Toggling `HotReloadConfig` itself needs a restart, since the watcher is created at startup.

## Sharing it with other people

`dist/SkillWeightMod-0.1.0.zip` is a drop-in package: BepInEx plus this mod, laid out so it
unzips straight into the Stolen Realm folder. It carries an `INSTALL.txt` aimed at someone who
has never modded the game. Rebuild it after changing the mod (see below).

### Multiplayer behaviour

Each client rolls its own skill options, for its own characters only:

- `PostBattleManager` queues level-ups only for characters passing
  `GameLogic.instance.AllMyCharacters.FastContains(character)`.
- `RoguelikeManager.CheckIfMyCharactersNeedLevels` iterates `Root.MyPartyCharacters`.
- `GetSkillChoices` is then called locally from `Update`, and only the *chosen* skill is
  synced — not the offered options.

There is no shared seed for the offer roll, so **a client-side reroll cannot desync a lobby**.
Consequences:

- Everyone who wants the effect must install it themselves; installing it does not change
  anyone else's rolls.
- Mixed lobbies are fine. Modded and unmodded players can play together.
- Config values do not need to match across players.

### Rebuilding the package

```sh
dotnet build -c Release
# then re-zip: BepInEx/ + winhttp.dll + doorstop_config.ini + .doorstop_version + INSTALL.txt
```

Ship no game files. The package bundles BepInEx 5.4.23.5 (LGPL-2.1), which is redistributable;
`Assembly-CSharp.dll` and everything else under `Stolen Realm_Data` is not.

## Building

Requires .NET SDK 8.

```sh
dotnet build -c Release
```

The build copies `SkillWeightMod.dll` into the game's `BepInEx/plugins/SkillWeightMod/`
automatically. If Steam is not on `C:`, override the game path:

```sh
dotnet build -c Release -p:GameDir="D:\SteamLibrary\steamapps\common\Stolen Realm"
```

## Failure behaviour

The prefix is wrapped in a try/catch and validates its inputs. On any unexpected state it
returns `true`, which runs the untouched original method. A broken mod degrades to vanilla
rolls rather than to a crash. Errors are logged once per occurrence to the BepInEx console.

## Known limitations

- **Tier distribution is untouched.** The mod changes *which* skill of a tier you see, not how
  often you see high tiers. Reweighting tiers by owned skills would be a further change to
  `RollTier`.
- **Options within one roll are independent.** All three offers are drawn from the same
  weighted pool, so a heavy specialisation can legitimately offer three skills from one tree.
  Repetition damping applies across rolls, not within one — the three options in a single
  level-up do not damp each other.
- **Offer history does not survive a reload.** It lives in memory for the duration of a run.
- **The reroll button's placement is best-effort.** It is positioned relative to Accept with a
  configurable offset; the game's own layout is not inspected beyond checking for a layout group.
- **Reroll costs are applied client-side**, consistent with the rest of the roll path being
  per-player, but the health write has not been verified in a live co-op session.
- **Multiplayer is fine, but per-player.** See "Sharing" below — the roll is client-side, so
  the mod only affects the characters of whoever installed it.
- **Game updates can break the patch.** Built against `Assembly-CSharp.dll` dated 2025-06-19.
  If `GetSkillChoices` changes signature, Harmony fails loudly at patch time; if its *internals*
  change, this mod silently keeps using the old logic. Re-check after a game update.
